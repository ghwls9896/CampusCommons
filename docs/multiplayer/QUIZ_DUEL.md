# 두 좌석 퀴즈 서버

`/v1/duel`은 도서관 퀴즈룸의 두 좌석을 한 경기로 연결한다. 같은 계정은 한 좌석만 차지할 수 있다. 서버 한 프로세스에서 좌석과 라운드를 메모리로 관리하므로 기존 로비와 같은 단일 워커로 실행한다.

| 호출 | 의미 |
|---|---|
| POST `/seats/0` 또는 `/seats/1` | 로그인한 사용자의 Bearer 토큰을 확인한다. 성공 응답에는 현재 상태, 좌석 티켓 및 Unix 초 단위의 `account_expires_at`이 담긴다. |
| POST `/seat/renew` | 갱신된 로그인 Bearer와 기존 티켓을 `X-Quiz-Seat-Ticket` 헤더로 보낸다. 같은 계정의 살아 있는 좌석만 연장하며 티켓·라운드·답안·타이머를 유지한다. |
| GET `/state` | 좌석 티켓으로 자기 상태를 확인하고 좌석 사용을 연장한다. |
| POST `/pdf?round_id=…` | 각자 자기 PDF를 application/pdf로 제출한다. start_page/end_page를 함께 지정할 수 있다. |
| POST `/draft`, POST `/answer` | 현재 round_id, level, choice, text를 전송한다. draft의 seq는 같은 단계에서 증가하는 저장 순서다. answer는 그 단계의 풀이를 끝낸다. |
| POST `/retry?round_id=…` | 일시적으로 실패한 출제 또는 채점을 재시도한다. 성공한 참가자의 출제·채점은 재사용한다. |
| DELETE `/seat` | 좌석을 반납한다. 경기 중 이탈하면 남은 자리도 다음 참가자를 기다린다. |

상태·제출·퇴장 요청은 임시 티켓을 Authorization 헤더에 넣는다. 참가자에게는 자기 문제만 전달한다. 양쪽의 세 단계 채점이 끝나면 점수·정답률·풀이 시간은 공유하고, 선택한 PDF에서 뽑은 문제·개인 답안·정답·해설은 해당 좌석의 응답에만 담는다.

서버는 로그인 만료 45초 전부터 시도하는 Unity 재인증을 받는다. 이전 서버 응답에 만료 필드가 없으면 Unity는 기존 폴링을 사용하므로, 장시간 경기에서 이 수정을 적용하려면 새 서버도 배포해야 한다. PDF 교체는 범위·용량 확인과 좌석·라운드 재확인이 끝난 뒤에 적용한다. 잘못된 교체 요청을 받으면 이전 자료와 이미 출제된 문제를 보존한다.

## 출제와 채점

두 좌석과 두 파일이 준비되어야 출제한다. Gemini에 각 PDF의 선택 범위를 개별 전송하고, 두 사람에게 같은 목표 레벨과 시간·인지 난이도 기준을 준다. 목표 레벨은 두 계정 레벨 평균을 반올림한 1~15 값이다. 양쪽 문제가 준비된 뒤 같은 서버 시각에 첫 타이머를 시작한다. 객관식 10초, 단답형 15초, 서술형 20초이며 제출하면 자기 다음 단계로 넘어간다. 시간 초과 때는 서버에 마지막으로 저장된 답을 사용한다.

한 문제는 10점이고 단답형·서술형은 기준별 부분점수를 받는다. 정답률은 만점 문항 수 / 3 × 100이다. 총 풀이 시간은 세 단계별 서버 경과 시간의 합이며 AI 대기 시간을 제외한다.

## 배포와 확인

기존 Render 서비스에 로그인용 SUPABASE_URL·SUPABASE_PUBLISHABLE_KEY와 출제·채점용 GEMINI_API_KEY가 필요하다. GEMINI_MODEL, DAILY_GENERATION_LIMIT는 기존 운영값을 사용한다. 1인용 호환 API와 2인 경기는 일일 AI 사용 한도를 공유한다. 실제 PDF를 제출하기 전 업로드할 수 있는 자료인지 확인한다.

Mac 두 창 시연에서는 좌석과 타이머만 Mac에서 관리한다. 동봉된 `run_quiz_pair.py`가 기존 퀴즈 서비스의 접속 설정으로 `HostedQuiz`를 구성한다. PDF 출제는 Render의 `POST /v1/quizzes`, 주관식 채점은 `POST /v1/quizzes/grade`를 사용한다. Gemini 키는 Render에서 관리한다.

배포 구성 시 `Tools/distribution/run_quiz_pair.py`를 시연 폴더의 `server/`에 복사하고, 기존 운영자용 `QuizConnection.json`을 같은 폴더에 준비한다. 키·접속 코드·개인 PDF를 저장소나 로그에 기록하지 않는다. 새 서비스는 선택적 `target_level`(1~15)을 적용한 경우에만 응답에 그 값을 담는다. 두 PDF에 공통 계정 난이도를 적용했는지 클라이언트는 `difficulty_mode`로 확인할 수 있다. `pending`은 확인 대기, `standard`는 기존 서비스의 기본 3단계, `account`는 계정 기준 출제를 뜻한다.

`backend` 디렉터리에서 `python -m pytest -q`를 실행한다. 외부 계정·모델 응답은 테스트 데이터로 주입한다. 실제 서비스 확인에는 서로 다른 계정 두 개와 서로 다른 시험용 PDF 두 개를 사용한다.
